# Обновление форка из upstream Telegram

Этот форк = официальный `telegramdesktop/tdesktop` + небольшой набор своих
коммитов (сейчас — панель pintopfp). «Обновиться» здесь означает **подтянуть
свежие изменения официального Telegram** (новые функции и фиксы безопасности),
сохранив свои правки сверху. Это делается слиянием истории git и пересборкой —
**не** встроенным автообновлением Telegram (оно бы затёрло ваш бинарник ванильным).

## Модель

- `dev` — чистое зеркало upstream (своих коммитов нет).
- `feature/pintopfp-panel` — это `dev` + ваши коммиты.
- Синхронизация: перенести ваши коммиты поверх свежего стабильного релиза
  Telegram, обновить сабмодули, пересобрать.

## Remote

Уже настроен:

```
upstream  https://github.com/telegramdesktop/tdesktop.git
```

Если его нет:

```
git remote add upstream https://github.com/telegramdesktop/tdesktop.git
```

## Как обновляться

Скрипт: `scripts/sync-upstream.ps1` (PowerShell).

### 1. Сухой прогон (ничего не меняет)

```powershell
./scripts/sync-upstream.ps1
```

Скачает upstream, определит последний стабильный тег (например, `v7.2.10`),
покажет: на сколько коммитов вы отстаёте, какие ваши коммиты будут перенесены
наверх, и есть ли незакоммиченные локальные правки.

### 2. Применить

```powershell
./scripts/sync-upstream.ps1 -Apply                 # на последний стабильный тег
./scripts/sync-upstream.ps1 -Apply -Tag v7.2.10    # на конкретный тег
```

По умолчанию это **rebase** — ваши коммиты аккуратно ложатся поверх нового
релиза (чистая линейная история). После него нужен force-push:

```powershell
git push --force-with-lease origin feature/pintopfp-panel
```

Если переписывать историю не хочется — используйте **merge** (без force-push,
но с merge-коммитами):

```powershell
./scripts/sync-upstream.ps1 -Apply -Merge
git push origin feature/pintopfp-panel
```

### 3. Пересобрать

После любого обновления **обязательно** обновляются сабмодули (скрипт делает это
сам) и проект пересобирается — апстрим часто двигает указатели сабмодулей и меняет
зависимости. Собирайте как обычно (см. `docs/building-win.md`).

## Что делает скрипт при `-Apply`

1. Ставит резервный тег `backup/pre-sync-<дата>` на текущий HEAD.
2. Авто-стэшит незакоммиченные правки (ваши сборочные хаки в `CMakeLists.txt`
   и сабмодуле `cmake`) и возвращает их в конце.
3. Делает rebase (или merge) ваших коммитов на выбранный тег.
4. Перематывает `dev` на тот же тег, если он остаётся чистым зеркалом.
5. `git submodule update --init --recursive`.
6. Возвращает застэшенные правки.

## Если возникли конфликты

Скрипт остановится и подскажет команды. Коротко:

- **rebase:** правите конфликтные файлы → `git add -A` → `git rebase --continue`
  (или отмена: `git rebase --abort`).
- **merge:** правите → `git add -A` → `git commit --no-edit`.

## Откат

```powershell
git reset --hard backup/pre-sync-<дата>
git stash pop        # если правки были застэшены и не вернулись
```

## Локальные сборочные правки

Сборочные хаки под Windows/16 ГБ хранятся так, чтобы переживать синхронизацию:

- **`Telegram/CMakeLists.txt`** (опция линкера MSVC, линковка `lib_crl`) —
  обычный коммит в ветке, переносится rebase'ом автоматически.
- **Сабмодуль `cmake`** (`/MP2` вместо `/MP`, снятие пина тулсета `v143`,
  Release PDB) — в сабмодуль закоммитить в родительский репозиторий нельзя, а
  `git submodule update` сбрасывает его рабочее дерево. Поэтому правки лежат в
  `patches/cmake-local-build.patch`, и скрипт **авто-применяет** их после
  обновления сабмодулей (идемпотентно).

Если поменяете сборочные правки в сабмодуле `cmake` — обновите патч:

```powershell
cd cmake ; git diff > ../patches/cmake-local-build.patch ; cd ..
```
